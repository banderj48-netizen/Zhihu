## 3. 可复现的关键问题

### A. 登录与初始化身份不兼容（阻塞）

[auth/repository.py:116](C:/Users/bcZho/Desktop/黑客松/Zhihu/backend/app/auth/repository.py:116) 产生字符串用户 ID，并持久化到本地 JSON；[initialization.py:27](C:/Users/bcZho/Desktop/黑客松/Zhihu/backend/agent/runtime/initialization.py:27) 直接插入 UUID 用户外键。

复现：传入同格式合成 ID 报 `InvalidTextRepresentation`；即使换成新 UUID，没先写 users 也报 `ForeignKeyViolation`。OAuth 当前路径没有创建正式 users 行，`/api/v1/me` 的 avatar 状态也没有从正式画像库回读。

同时 `database.initialize()` 只运行旧 schema 和 002/003，正式表需手工执行；旧测评/领域接口操作 `avatars`，正式仓储操作 `user_avatars`。两套同名 users 的 ID 类型不能混用。

### B. 完成初始化路由永远被前面的通用步骤匹配（阻塞）

[api.py:123](C:/Users/bcZho/Desktop/黑客松/Zhihu/backend/agent/runtime/api.py:123) 先注册 `POST /initializations/{session_id}/{step}`，之后才注册 `/complete`。

用原文件 AST 中的实际路由和请求 DTO，配合模拟服务在 FastAPI TestClient 复现：发送 `{identity: {...}}` 到 `/complete`，实际调用 `save_step(session_id, "complete", {})`，真正的 complete 调用次数为 0。identity 被忽略，可能返回 200 却没有生成画像。

这是路由调度验证，不冒充整站 HTTP E2E；未伪造 LangGraph 依赖后宣称启动成功。

### C. 初始化显示 completed，但核心画像为空（阻塞）

[initialization.py:52](C:/Users/bcZho/Desktop/黑客松/Zhihu/backend/agent/runtime/initialization.py:52) 只把 `personality` 原样传仓储，未用已导入的 `score_assessment`，未消费 domains/opinion-answers/social-answers/import_job_id。

真实 PostgreSQL 隔离复现：提交 50 题原始答案、领域、观点答案和社交答案后，直接调用 complete，返回 completed，但：

```json
{
  "scores": {},
  "avatar_memories": 0,
  "source_documents": 0,
  "avatar_style_examples": 0,
  "vector_sync_outbox": 0
}
```

如果改为传入评分器的完整结果，`status=completed` 又违反 `avatar_personality.status` 仅允许 confirmed/unconfirmed/rejected 的 CHECK。必须分别建模“测评完成状态”和“画像确认状态”。不能丢掉测评版本和原始答案。

### D. 三种匹配的实际接口 provider 类型错误（阻塞）

[matching.py:21](C:/Users/bcZho/Desktop/黑客松/Zhihu/backend/agent/runtime/matching.py:21) 使用 `await self._provider(scene_id)`，而 API 注入的 [PresenceService.list_candidates](C:/Users/bcZho/Desktop/黑客松/Zhihu/backend/agent/runtime/presence.py:33) 是同步函数，返回 list。复现报 `TypeError`，发生在模式分支之前，三种模式均受影响。

即使修复 await，LLM 匹配 Prompt 只有 candidates，没有当前 A 的性格/兴趣/观点，无法按 PRD 比较“谁最适合当前用户”。在场创建仅在选出 B 之后执行，尚缺普通用户先进入场景的完整入口，空库依赖外部建候选。

### E. Agent tools 并非完整可用的修改闭环（高）

[dialogue.py:77](C:/Users/bcZho/Desktop/黑客松/Zhihu/backend/agent/runtime/dialogue.py:77) 只注册行为工具；其余观点/兴趣等目前只是 Python 包装。绑定 `base_version_id=None` 导致仓储的可选版本检查被跳过。

[model_builder.py:50](C:/Users/bcZho/Desktop/黑客松/Zhihu/backend/agent/runtime/model_builder.py:50) 要求返回非空 content，合法的 tool-only response（content=null，含 tool_calls）会报 RuntimeError，已用模拟 HTTP 响应复现。即使 content 非空，图从顶层 raw 读取 tool_calls，而标准响应位于 `choices[0].message.tool_calls`；参数也没从 OpenAI 格式转换为 LangChain 调用格式。

写仓储目前只有 INSERT 新记忆；不存在 target_memory_id 修订/替代/撤销操作。`source_refs` 仅写入 last_change，未自动建立证据关系。工具层 status=confirmed 缺少可信用户确认事件依据，不能以模型自己填字段代替用户确认。

### F. 完整画像版本、证据和普通写函数仍不完整（高）

[repository.py:51](C:/Users/bcZho/Desktop/黑客松/Zhihu/backend/agent/profile/repository.py:51) 拷贝旧 snapshot 后只更新 last_change，不把正式记忆列表合并进去。复现新增行为记忆后 snapshot.memories 仍为空，source_refs 对应 memory_evidence 为 0。

当前 [functions.py](C:/Users/bcZho/Desktop/黑客松/Zhihu/backend/agent/profile/functions.py:7) 只有初始化、原文、会话、消息、证据这五个入口；没有分别更新固定身份/性格/风格/策略/检索规则、写入真实风格样例与成长评估的完整函数。已有版本号和 active 唯一性不等于“任意画像动态修改、完整快照回滚”已经实现。

`add_memory_evidence` 单独写入没有版本/审计，也未校验引用文本与原文的一致性。`write_source` 按全局 `(platform,external_id)` 冲突更新内容，不能完整表达不同用户持有同一公开资料和原文修订历史。

### G. RAG 默认未接真实向量，行为和对话上下文不满足 PRD（高）

[api.py:56](C:/Users/bcZho/Desktop/黑客松/Zhihu/backend/agent/runtime/api.py:56) 硬编码 `_EmptyVector()`，不是“仅 Chroma 故障时降级”。当前无需读取环境即可确认默认实际向量召回永远为空。

[retrieval/service.py:29](C:/Users/bcZho/Desktop/黑客松/Zhihu/backend/agent/retrieval/service.py:29) 是正则规则分析，未做 LLM 意图改写。行为记忆参与通用候选池，但没有每轮独立行为语义检索，可能被其他类型挤出；中文关键词常是整个短句，依赖空向量时语义近似内容容易漏召回。

[agent_graph.py:62](C:/Users/bcZho/Desktop/黑客松/Zhihu/backend/agent/runtime/agent_graph.py:62) 构建的是 context/messages/question JSON，没有 PRD 导演 system 指令。场景仅用于最初开场，之后 _run_turn 不传 scene。每轮 messages=[]，聊天历史只靠相关性命中窗口，不能保证最近对话和关系上下文连续。当前最后一条通常由 B 输出，与 PRD “开场方负责结束”不一致。

### H. 高质量判定和心灵感应成长未实现 PRD 规则（高）

[dialogue.py:132](C:/Users/bcZho/Desktop/黑客松/Zhihu/backend/agent/runtime/dialogue.py:132) 后的评分只有固定 score 阈值；代码不查历史评分分布。`score > 0.8` 与“超过历史 80% 对话”不同。

[mind_reading.py:19](C:/Users/bcZho/Desktop/黑客松/Zhihu/backend/agent/runtime/mind_reading.py:19) 只比较 option_id 并 UPDATE feedback。隔离复现发现任意不存在选项也可提交，已答题可再次覆盖；匹配/不匹配后性格调整表和成长评估表均 0 条。

对话没有自动采集 no-hit→生成题目→用户选择→写记忆/证据→累计性格方向→达到阈值生成版本的调用链。

### I. 向量任务不具备完整失败/删除一致性（高）

[outbox.py:11](C:/Users/bcZho/Desktop/黑客松/Zhihu/backend/agent/profile/outbox.py:11) 只选 pending，失败后设 failed；下一次运行不会自动重试。未处理 operation=delete、processing 超时接管或拒绝/失效过滤，且外部 await 仍发生在读取实体的数据库连接上下文内。

隔离复现：第一次向量失败，下一次 worker processed=0；将源记忆设 rejected 后再次 pending，同步成功且 rejected 记录进入适配器。

原文/聊天仓储没有创建对应 outbox；聊天直接 upsert 失败时仅 pass。聊天直写 metadata 无 avatar_id，而检索按 avatar_id 过滤；实际向量无法按该契约命中。现有测试适配器故意忽略过滤，不能验证真实 Chroma 过滤语义。

### J. 原文与角色卡还有数据正确性问题（中）

[chat_repository.py:15](C:/Users/bcZho/Desktop/黑客松/Zhihu/backend/agent/profile/chat_repository.py:15) 同一 client_message_id 重试会 DO UPDATE content；复现可将原始消息改成另一文本，违背不可变原文。应区分同内容幂等重试和不同内容冲突。

[card_renderer.py:6](C:/Users/bcZho/Desktop/黑客松/Zhihu/backend/agent/profile/card_renderer.py:6) 的 JSON 转换不处理 Decimal，非空置信度导致 `json.dumps(card)` 报 TypeError。卡片记忆未按 valid_until 过滤、private 内容直接 enabled，未区分所有者内部上下文与可分享导出，也未保护 structured_data 中原始答题/私密备注。

### K. 鉴权前置尚未覆盖所有入口（高）

用户要求归属校验在进入 Agent 修改前完成，这一边界合理；当前 HTTP 接入层尚没有统一做到。初始化读取/保存/完成、心灵感应作答、SSE 和取消没有统一 session 用户绑定。`get_dialogue` 仅在 result 存在且传 X-User-Id 时才校验；SSE/取消依赖 run_id 本身不足以证明权限。

这不是要求 Agent 内再建一套登录系统，而是必须在调用服务和创建绑定工具前固定可信用户上下文。

另外，并发占用失败分支会无条件 release A/B，可能释放他人正在使用的 Agent。应只释放本请求成功占用的记录；不要凭 avatar+scene 释放无归属运行。

## 5. PRD 中需统一的产品规则

以下是需求表述待统一，不应以此阻止已明确功能开发：

1. 资料范围：此前确定简介+回答，当前 PRD 增加帖子。建议新 PRD 为准，明确 pin 与 article 是否都包含，并区分摘要和原文。官方 OAuth 列表权限不等于任意用户全文权限。
2. 风格样例：固定选项及 LLM 出题文本不是用户真实表达。只能从用户原文、自定义答案等真实文本选取 style_examples；不能把 3/4/5 的固定选项直接当用户语料。
3. 性格成长：单次观点不同不必然意味着性格错。先写具体情境记忆，再根据多次同方向、有来源的证据微调，保留不确定性、阈值和历史。
4. 评分历史范围：明确按当前用户、双方组合还是全站历史；第三/四场排名是否包含本场，并列第一如何处理。当前固定 0.8 均不满足这些解释。
5. 轮数：现代码是 10 个 A/B 往返、最多 20 条，PRD 写最多 20 轮。应统一“轮”的定义以及由开场方结束的规则。
6. 分享与私密：默认私密允许所有者 Agent 用于生成回答，但不能直接公开完整画像、原始答案和私密注释。明确高质量通知中的知乎主页展示边界。

## 6. 建议补齐顺序与验收

1. **统一身份、数据库和迁移入口**：OAuth 外部 ID 映射内部 UUID，正式 users 先创建；测评/领域切换正式画像关系，当前登录与分身状态从同一事实源读取。修复 complete 路由。
2. **贯通初始化**：接入导入摘要/原文→证据、服务端测评→人格 DTO、题目生成/版本/选项、13 秒验证、LLM 分类→动态记忆、风格原文样例、完整初始快照。同一主事务落库并创建 outbox。
3. **补齐读写与成长基础**：固定字段普通函数、可信确认、记忆修改/过期/证据工具、完整快照和回滚、正式画像/卡片读取接口；不把普通写函数全部注册给 Agent。
4. **接通对话**：修复 provider、在场占用；比较 A 与候选画像；每轮注入导演/场景/最近历史，业务显式检索真实 Chroma 并保证行为通道，修复工具协议。
5. **接通反馈**：无命中事件→含 Agent 实答的选择题→用户确认→记忆与证据→性格累计调整/成长评估；实现历史分位评分和用户可见通知事实。
6. **端到端验收**：隔离 UUID 数据库下从登录模拟回调起走真实 HTTP 全链；验证答案不丢、超时不入记忆、已有画像可修订、工具真实协议、撤销与向量失败重试、同一用户隐私和 A/B 消息连续性。真实模型与 embedding 验收单独报告，不用契约 double 代替。

目前最先需要做的不是继续增加接口数量，而是让现有入口使用同一用户身份、同一正式 schema 和同一条初始化/对话/反馈数据流。
